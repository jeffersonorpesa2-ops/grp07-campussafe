# CampusSafe — Application Roles to Database Roles Mapping

**System:** CampusSafe: Campus Hazard & Safety Reporting System  
**Course:** COMP 018 Database Administration  
**Group:** Group 7  
**Database:** `grp07_campussafedb` (PostgreSQL 14+)  

---

## 1. Architectural Philosophy: Application Roles vs. Database Roles

In modern web applications, **application users do not receive individual PostgreSQL logins**. Creating a direct database account for every student, faculty member, or staff technician would violate security principles, exhaust connection limits, and break session pooling.

Instead:
1. **PHP Application Runtime Account (`campussafe_app`):** Connects to PostgreSQL on behalf of the application, authenticated through credentials defined in `.env`.
2. **Session-Level Role Guard (`src/auth/Auth.php`):** Authenticates human users via bcrypt password verification, assigns an application role in `$_SESSION['user']['role_name']`, and strictly enforces role permissions server-side on every route and form action.
3. **Database Role Privileges (`database/03_roles_and_privileges.sql`):** The underlying database accounts are locked down with the **Principle of Least Privilege (PoLP)**. The runtime account cannot execute schema modifications (`CREATE TABLE`, `DROP TABLE`), while read-only accounts cannot view user password hashes.

## 3. Least-Privilege Design Rationale

1. **Restricted Deletion (`DELETE` Narrowing):**
   - The runtime account `app_runtime_grp` is intentionally **NOT** granted `DELETE` on `hazard_report` or `app_user`.
   - Campus safety records must maintain legal and institutional audit trails. Reports are closed, never deleted. Users are deactivated via `account_status = 'inactive'`, preventing cascade destruction of historical incident logs.
   - `DELETE` is only granted on `attachment` (to remove misfiled files) and `assignment` (to reassign work).

2. **Auditor Credential Protection:**
   - The `app_readonly_grp` (and login `campussafe_report`) has **no SELECT grant on `app_user`**.
   - This guarantees that an auditor or read-only report generator can never dump password hashes even if they connect via SQL CLI or BI tools.

3. **Public Schema Lockdown:**
   - `REVOKE ALL ON DATABASE grp07_campussafedb FROM PUBLIC;`
   - `REVOKE CREATE ON SCHEMA public FROM PUBLIC;`
   - Prevents unauthorized database users from creating rogue tables or inspecting data.

## 4. Application-Level Role Guarding Implementation

All role checks occur on the server in `src/auth/Auth.php`:

```php
// Enforce user authentication
Auth::requireLogin();

// Enforce specific role authorization
Auth::requireRole('Administrator');

// Multi-role permission check
Auth::requireRole(['Administrator', 'Auditor']);
```

If an unauthorized user attempts to manipulate URL endpoints, `Auth::requireRole()` immediately terminates execution, logs the incident, and returns an HTTP `403 Forbidden` response.
